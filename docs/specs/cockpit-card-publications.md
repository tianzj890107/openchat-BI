# Cockpit AI 插槽交付与上次成功内容

2026-10-26实现；本轮尚未部署。适用于主服务 main 路线，AP连接与原有本体／数据库连接规则不变。

## 用户可见行为

- 所有12个AI插槽复用已交付的组件和卡片布局，主服务不再用通用长正文块替代它们。
- 进入页面先读取服务端保留的默认筛选范围的上次成功卡片，无需等待本次模型分析。
- 页面正常读取本次AP数据后，按实际查询范围取同范围的卡片并静默更新。AP数值未变且上次分析未满5分钟时复用；变化或过期则后台分析。
- 后台成功后整组替换对应环节的卡片；用户不用刷新页面。中间草稿不回填，更新失败继续保留旧内容与原分析时间。
- 切换筛选后立即清空上一范围的卡片；有该范围缓存则展示缓存，无缓存则显示各AI插槽内的加载骨架。迟到旧响应不能覆盖新范围。
- 首次建立某范围、服务器尚无成功结果时，需要完成一次分析。部署前应预热默认页面，不能用硬编码文案伪造“已完成”。

更新以页面打开、图表成功取数／筛选变化为触发；不在没有新图表数据时独立定时重查其他数据源。

## 主服务交付契约

新增只在Cockpit临时会话开放的 `CockpitDeliverCards`。仍由现有WebSession循环执行：

```text
意图路由 → 读取Cockpit-DashboardQuery及证据ID → 主模型提交CockpitDeliverCards
       → 引用与因果校验 → 主服务最终交付校验 → 发布完整卡片
```

卡片契约 `cockpit-cards-v1` 包含 `summary`、`causes`、`recommendations`、`limitations`。
沿用现有原因／建议字段、证据引用和短内容约束，没有另开LLM格式化链路。
未读数据、未知引用、汇总事实冒充已证实原因、建议引用未知原因均被拒绝。
缺少证据允许交付空原因／空建议，并在原卡片结构中说明缺失，不能为了填满界面编造。
交付工具之后若又查询了新数据，之前的卡片候选失效，必须重新提交。
最终校验未通过、needs_input、取消、失败或没有有效卡片契约时，不覆盖上次成功版本。
完整主服务正文仍保留在历史和报告中，用于追溯；看板只绑定短摘要、事实、原因和建议。

AP原始行不能按“原因”归组后展示虚构的金额／订单数量；因果不明时展示待核实。
事实缺失显示未提供或横线，不把未知值转换为零。主服务卡片不再显示旧协议的2025-10标签作为真实查询范围。

## 持久化与范围

继续使用 `dataset/cockpit/history.sqlite3`，仅追加两个表：

- `publications`：稳定范围 → 最后成功分析ID，原分析记录不覆盖。
- `publication_views`：默认页面／环节 → 已成功发布范围，首次绘制从这里读取。

范围包括固定身份、引擎、页面、环节、AP连接标识、实际AP请求（包括筛选条件）、明确补充口径、元数据版本和卡片契约。
不把每次变化的receiptId、取数时间或响应值当作筛选范围。AP响应内容单独计算dataFingerprint用于判断是否需要更新。
不同身份、来源、筛选、页面不会互相借用缓存。AP凭据过期不删除已发布卡片，新分析仍须使用有效的本次取数凭据。
指针只在新任务完成且卡片有效后更新；任务创建时间更早的迟到结果不能覆盖更晚的成功结果。
服务器重启后从SQLite恢复上次成功卡片，未完成任务标为中断，不清空旧发布。
默认页面指针只接受默认范围的成功交付，切换筛选产生的结果不会替换默认页面内容。

## 接口

| 接口 | 用途 |
| --- | --- |
| GET `/api/cockpit/analyses/published?id=1&engine=main&page=analysis` | 返回默认范围各环节上次成功卡片 |
| POST `/api/cockpit/analyses/refresh` | 与原分析相同的范围和AP凭据，增加page和defaultView；立即返回cached、analysis、refreshing |
| GET `/api/cockpit/analyses/{id}` | 后台任务轮询，成功后自动替换卡片 |

刷新接口复用原任务、准入、独立分析并发、取消和全站引擎锁定。相同范围的进行中任务去重；显式refresh可强制更新。
新接口不会绕过生产环境唯一引擎配置。旧 `/analyses`、报告、历史和任务接口保留。

## 部署与默认页面预热

需要在新的明确部署授权下同时更新8765代码和8876静态资源；AP地址、独立认证文件与数据目录沿用现配置。
8877仍保持停止，不为缓存新增服务。首次部署自动追加表，不删除、迁移或覆盖历史会话和旧分析。

在切正式流量前，通过临时入口逐一打开两个固定身份的默认页面及所需默认节点，等待默认卡片发布完成。
用published接口确认相应环节已有 `cardContract=cockpit-cards-v1` 的完整结果；然后再切正式入口。
这样普通用户首次打开即可读取服务端预热内容。新筛选范围第一次访问仍使用设计内的加载态。
旧版长正文没有这个契约，不能把它直接当作完整卡片缓存，也不能拿原型数据冒充真实预热结果。
