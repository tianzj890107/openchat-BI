# 商机获取节点 V3 规则卡实现说明

## 目标

`opportunity-risk` 卡以《亿纬锂能_本体_商机获取节点_V3》为准，独立读取客户数据库、执行固定规则并发布，不再复用共享 `opportunity` 阶段卡片。程序负责阈值、数值、规则触发与候选关系；每轮调用一次模型，由模型结合规则结果和证据生成摘要、风险说明、原因和建议，程序再校验代码、数字、证据与关联边界。V2 运行配置 `assets/opportunity-v2/config.json` 保留用于历史兼容，当前运行时只读取 V3 配置。

## 运行链路

1. `scripts/build_opportunity_v3_config.py` 从 V3 本体和数据字典生成并校验 `bi_agent/cockpit/assets/opportunity-v3/config.json`，保留源文件 SHA256、25 个指标、10 类风险、9 类原因（RC01～RC09）、12 类行动建议（AC01～AC12）和风险关联。建议配置同时保留作用对象、责任角色、原始期限、目标值、验收标准、跟踪指标和优先级。
2. `bi_agent/cockpit/opportunity_v2.py` 只使用已校验的表字段映射和参数化 SQL，读取目标、月度预测、合同确认、客户等级、产品、阶段、投标、订单关系、项目进展和团队关系。所有数据库查询在同一个 `REPEATABLE READ` 快照内完成：主连接导出快照，另外两条连接导入同一快照，独立查询最多 3 路并行。每条查询使用独立 savepoint，单条 SQL 失败回滚后不污染同快照的后续可选查询。单条 SQL 上限 30 秒，数据库取证阶段上限 60 秒；总预算耗尽时取消未完成查询，已返回结果保留。
3. 程序计算指标并执行 RK01～RK10；金额和电量分别计算，不互相折算；动态周期严格大于同阶段、同产品类型均值的 1.5 倍才判超期。
4. 每次规则计算后调用一次模型。输入包括全部 RK01～RK10 候选、每个候选的 `ruleStatus=triggered/not_triggered/insufficient/not_applicable`、规则原文、已观测事实、缺失输入、本体允许的原因/建议候选和对应进展片段；程序不先筛掉未命中风险。模型必须对每个候选风险恰好返回一次判断，可标记 `confirmed/structural/insufficient/not_applicable`，并分别引用支持证据与反对（反例）证据，再生成摘要、原因和建议。只有程序已触发且模型确认的风险可以展示；模型不能把程序计算的未命中数值规则改判为成立，对已触发规则可以降级为证据不足或结构表现。程序校验风险/原因/建议代码、风险—原因—建议关联、数字只能来自输入、支持与反对证据必须可追溯且不得使用“逾期未完成”。越界项、漏答和重复判断不进入展示，并让本轮标记为 `partial` 或 `fallback`。模型失败或全部输出被拒绝时本轮不发布，冻结版本继续保留上次业务分析，同时保存失败诊断；首次没有旧卡时显示可重试的分析未完成状态。
5. `opportunity-risk` 作为独立 publication key 写入冻结年度版本。前端只读取该 slot 自己的已发布 payload，不再用共享阶段 `state.item` 按时间戳与之比较；点击该卡的“重新分析”只刷新 `opportunity-risk` 队列项。整页重算时商机节点的分阶段卡片交给独立分析流程更新，`opportunity-coverage-note` 和其他卡片继续使用共享 `opportunity` 结果。共享卡晚于专用卡完成、专用卡晚于共享卡完成两种顺序都有回归测试。
6. 专用分析通过同一个进度回调依次上报“读取本体 → 查询数据库（当前查询名、完成数/总数、本查询耗时）→ AP 补充（如需要）→ 规则计算 → 原因分析 → 发布”；前端固定按 `opportunity-risk` 读取该卡进度和耗时，不跟随历史发布结果中的共享 `opportunity` 键。
7. 冻结发布卡不写入普通分析历史表。草稿与任务下发通过年度发布版本按 `analysis id` 回查完整卡片、证据和建议，避免返回“分析记录不存在”。

## 固定口径

- 签单按 `new_contractconfirmation=1` 判断；`0` 为未确认，空值或其他值不当作零值或已签。
- 已确认签订覆盖率（实现口径）为“合同已确认商机预测 ÷ 目标”，金额和电量分别计算；合同状态未知既不进入已签，也不进入明确未签或进度滞后触发。季度待签窗口只使用明确未确认金额或电量加预测缺口。
- 客户等级：战略 `0/1`、重点 `2/4`、一般 `3`，其他值不推断。
- 项目阶段只映射 `11～15 → P0～P4`。
- 目标表按行求和，不按客户或产品做无业务键依据的 `DISTINCT`。
- 目标字段全部为空时保留 `NULL`，表示“未取得目标”，不转成 0；数据库返回的真实 0 是有效值，可以与空值区分。
- 预测电量使用覆盖稳定的 `new_orderforecast_qty`（kWh）换算 GWh；`new_forcastpower` 的实库空值只在限制中披露。
- 商机、投标和进展按测量日过滤；在途记录算至测量日，完成记录算至结束时间。目标、订单等无业务时间键的数据不做无依据的时间截断，并在口径中说明。
- 查询结果达到行数上限时标记 `ROW_LIMIT` 并将卡片置为 `limited`；展示明细可以截断，但金额、电量、合同、产品、客户和风险总量只使用全量聚合。全量聚合本身失败时，截断明细不参与这些计算，相关规则不触发。
- 投标关联仅使用去首尾空格后的精确项目名称。同名多条记录判为歧义，不据此认定“未投标”。
- “有商机未投标”只统计当前在推商机；历史商机不遮挡当前问题。
- 需求未确认只接受明确状态 `1/2/4/5`；状态为空表示未知，不默认算作未确认。
- 战略客户无商机区分“从未建立商机”和“历史有商机、当前无在推商机”。RK07 只关联 RC09，不再关联 RC01，避免同一客户范围内出现互相矛盾的条件。
- RC09 以近 90 天为默认窗口，检查客户主数据的最近拜访、最近销售活动和最近线索时间，并补查线索表与线索进展表；来源完整时才判定“开拓不足”，来源未接通时只能记为数据缺口。
- 建议期限保留本体原文：`按月`、`按突破计划协同` 等文本不折算成固定 30 天；`deadlineDays` 只用于任务令的日期兜底。
- AC05“补建投标前置条件台账”来自数据治理，标记为 `investigation/governance`，不占用重点业务改善建议的位置。
- AC10 的目标表述为“重点跟踪覆盖率提升到 70%”，不解释为客户结构或预测结构占比。
- RC04、RC05 只作结构定位，不单独证明待签或转化受阻。
- 每项规则保存四种状态：`triggered`、`not_triggered`、`insufficient`、`not_applicable`。任一必需事实为空、查询失败或未知时，`ruleStatus` 为 `insufficient`，不得当作 `not_triggered`；只有必需事实齐全且业务范围明确为空时才可标记 `not_applicable`。模型只能把未触发的事实判为证据不足或不适用，不能确认风险成立。
- 模型判断结果逐条写入 `riskAssessments`，包含 `include/classification/evidenceIds/supportingEvidenceIds/opposingEvidenceIds/assessmentSource`。最终未展示的候选写入 `excludedRiskCodes`，模型主动排除项另写 `modelExcludedRiskCodes`。
- 模型状态必须区分：`completed` 表示全部候选风险逐项判断且摘要、原因、建议均采用模型结果；`partial` 表示至少一部分模型结果被采用，但存在漏答、越界拒绝或模板补充；`fallback` 表示没有可采用的模型内容；`failed` 表示模型调用或解析失败。`fallback/failed` 不覆盖已发布卡片；`partial` 可以发布，但必须在诊断中列明覆盖数量和回退项。
- `analysedRiskCount` 记录模型实际有效判断的候选风险数，`missingRiskCodes` 记录漏答或校验未通过的候选；`riskCandidateCount` 固定为全部本体候选数。`riskTotalCount` 必须等于最终展示的 `riskCodes` 数量，模型排除风险后同步减少；程序原始触发数单独记录为 `ruleTriggeredRiskCount`。
- 模型漏答不会删除程序已触发风险，但该风险使用规则降级判断并将整卡标为 `partial`，不能显示为完整模型分析。
- 重新分析按风险合并上一版结果：本轮有充分模型判断的风险更新对应风险、原因和建议；本轮未覆盖、模型漏答或证据不足的风险保留上一版的发布时间和来源；只有模型明确判定 `not_applicable` 才移除旧风险。展示层新增 `retainedRiskCodes/retention`，并说明保留项。
- 证据计数统一为 `facts`（数值事实）、`records`（明细记录）、`referenced`（引用证据）、`distinct`（去重后的证据数）。卡片头部、折叠区、完整证据页和交付状态使用同一组计数。

## 失败与降级

- 单个可选查询失败时保留其他已取证据，依赖缺失指标的规则不触发，卡片状态为 `limited`。
- 目标、商机、客户等核心查询全部失败且没有任何可保留证据时，本轮不发布，冻结版本继续使用上次成功卡片。
- 数据库真实零值和规则未触发是有效结果，不以 AP 或模型补造风险。
- 数据库核心取数失败时允许走 AP 聚合补缺路径，AP 结果与数据库结果使用同一套模型判断；只有目标金额和目标/预测电量等核心聚合足以形成证据时才发布。AP 不替换数据库成功返回的值，也不补造商机明细、合同状态或原因文本。当前映射 `目标销售额`、`目标出货量`、`商机获取金额`、`商机获取电量`；`待突破战略客户数` 等语义不一致的指标不参与补充。
- 可通过 `COCKPIT_OPPORTUNITY_V2_AP_SUPPLEMENT=0` 关闭 AP 补缺；关闭后数据库缺失指标的规则保持不触发，卡片按已有证据以 `limited` 发布。
- 数据库返回真实零值或规则未触发时不再请求 AP；只有字段缺失、查询失败、覆盖不足或行截断才进入补缺路径。
- 项目进展文本用于模型解释已触发风险的原因，不参与风险阈值判定；模型不可新增风险、原因或建议代码。程序生成的数据缺口、查询失败和模型失败进入 `dataDiagnostics` 与后台诊断，不再混入业务口径说明；固定口径说明单独保存为 `caliberNotes`。
- 数据库失败按连接、查询名、SQLSTATE、耗时和诊断 ID 记录，后台可查脱敏后的原始原因；公开卡片不返回驱动原始消息。
- 风险卡正文中的数值与单位按共同问题分析卡样式统一显示为蓝色强调；建议条目展示责任角色，仅清理“牵头、协同、配合、支持、执行、负责”等明确括号后缀，任务令继续使用原始角色字段。
