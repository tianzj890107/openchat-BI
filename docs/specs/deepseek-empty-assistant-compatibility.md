# DeepSeek assistant-message compatibility

2026-11-09. Customer diagnostics identified DeepSeek 400 errors: `Invalid assistant message: content or tool_calls must be set`. The shared Team provider uses the DeepSeek message converter. Empty or reasoning-only persisted assistant blocks were previously emitted as `content:null` without tool calls.

The outgoing converter now omits assistant turns with no nonblank text and no tool calls, including empty string turns. It preserves tool-only messages, tool-call IDs, tool results and reasoning for valid assistant turns when thinking is enabled. Stored conversation history is never rewritten. Both direct DeepSeek and Team/LiteLLM use this projection.

When the selected Team model is DeepSeek, automatic quota/rate-limit fallbacks remain within DeepSeek-named routes. This prevents silently selecting MiMo/GLM/etc from a stale gateway catalogue. It does not verify advertised gateway routes or change their configuration; ordinary 400 errors are not retried as quota failures. Existing TEAM_BASE_URL and TEAM_MODEL remain authoritative.

Validation: 230 tests passed, plus 42 subtests (message conversion, tool pairing, thinking modes, fallback catalogue and existing regression suite). No live model calls, gateway writes, customer configuration edits, tar changes or deployment. AP query-combination gaps and missing quotation metrics are separate issues and are not addressed by this patch.

## Server-preloaded evidence and hidden reasoning (2026-11-09)

Customer diagnostics after bounded pre-reading showed a different 400: DeepSeek required `reasoning_content` before the first meaningful analysis response. The server had inserted synthetic assistant tool calls for its own frozen evidence reads. These calls were not generated by DeepSeek and had no actual model reasoning to replay.

Preloaded reads now still execute through the normal tool boundary, record claims and emit progress events, but their results enter the model as a separate user observation packet. They do not become fabricated assistant/tool history. Subsequent model-requested tool calls keep the normal assistant/tool protocol, evidence validation and immediate validated-delivery behavior. Page phase/timing remains independent of that request history.

DeepSeek/Team tool-enabled requests now preserve actual provider-returned thinking blocks independently from the UI visibility toggle, including when a gateway returns reasoning despite an explicitly disabled request. No reasoning is fabricated or displayed to the page. The requested thinking mode is unchanged. Plain non-tool chat and non-DeepSeek Team routes retain their existing projection behavior. This follows the [DeepSeek tool-call protocol](https://api-docs.deepseek.com/guides/thinking_mode/#tool-calls).

Validation includes strict first-request projection checks, hidden-reasoning replay with differing environment/request modes, direct DeepSeek replay, existing one-call delivery and repair cases. A live, minimal two-request protocol probe against the existing team gateway and `direct-deepseek-v4-flash` succeeded with the changed Team adapter: real reasoning was retained for the next call without visible thinking deltas. Probe inputs were synthetic, involved no AP/PG query and dispatched no business task. No gateway settings, customer env, runtime history, tar or deployed service was changed.

Current compatibility validation: 661 Python tests and 69 subtests passed; all 106 Cockpit Node tests passed. The live changed-adapter probe completed both the initial synthetic-observation request and the real tool-result follow-up against the team gateway, with hidden reasoning preserved internally.
