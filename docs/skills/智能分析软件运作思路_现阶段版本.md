# 智能分析软件运作的完整思路(现阶段版本)

## 前言:现阶段的能力边界

现阶段系统建立在 **单 Agent + 本体知识库(Excel 形态)+ 大模型 + Agent Loop** 的架构之上。相比完整形态的"多 Agent 协作 + 本体图谱 + Link 驱动的多跳归因",现阶段聚焦于 **用更轻的架构把核心闭环先跑起来** —— 把本体知识库作为上下文的主要来源,通过精确的上下文准备让大模型在单 Agent 框架下完成高质量的问答和分析,归因能力主要依靠 **上下文里已经组装好的对象、属性、流程、指标关系** 而不是运行时的图谱多跳。

这个选择不是妥协,而是务实 —— 它让产品能快速落地并在真实使用中验证价值,同时为后续演进到完整形态(引入 Link Types、因果模型、多 Agent 协作)留足空间。

下面按照六步骤展开完整思路。

---

## 第一步:用户意图识别 —— 把"模糊问题"变成"可执行问题"

### 核心任务

用户提的问题往往是模糊的 —— "上月华东区怎么样"、"为什么这批货质量不行"、"明年要不要扩产"。这些问题要被系统执行,必须先把它 **结构化**:想看什么、想分析什么、关键词指什么、该用什么路径回答。

### 三件事并行进行

**1. 角色识别与 Agent 角色确定**

系统结合用户的组织角色(销售总监 / 工厂厂长 / 财务分析师 / 高管)和问题语义,确定当前 Agent 扮演什么角色回答 —— 是业绩分析师、质量工程师、还是战略参谋。

这里的"Agent 角色"不是激活多个独立 Agent,而是给 **同一个 Agent 设定当前工作的人格和分析视角**,让它用对应角色的专业口吻和关注点来处理问题。角色决定了后续上下文侧重、回答风格、术语选择。

**2. 术语消歧**

用户说"客户活跃度",系统里可能对应三个口径(月活、周活、订单活跃);用户说"华东区",可能对应行政区划也可能对应业务大区。系统检索术语库:

- 有唯一对应 → 直接使用
- 有歧义 → 先尝试基于上下文(用户角色、最近会话、所在部门)**自动消歧**
- **自动消歧失败则必须让用户手动选择**

这一步的原则是 **宁可多问一次,不能默默走错** —— 后面所有计算都基于这个口径,口径错了全盘皆错。

**3. 复杂度评估与回答模板匹配**

系统判断问题是哪一类:

- **简单查询**("上月销售额多少")
- **浅度分析**("销售额为什么下降")
- **深度归因**("下降的根本原因和影响因子")
- **决策建议**("应该如何应对")

不同复杂度对应不同的回答模板和后续流程深度 —— 简单查询走快速路径,深度分析走完整的 Agent Loop。**复杂度评估的价值在于让资源消耗匹配问题价值**,不要用大炮打蚊子,也不要用蚊拍打老虎。

### 本体知识库在这一步的支撑

术语库本身就是本体知识库的一部分 —— Excel 里维护着每个业务术语对应的对象、属性、指标、维度。消歧的本质是 **把自然语言映射到本体知识库中的具体条目**。现阶段虽然本体存在 Excel 里,但通过预先做好向量索引,术语检索依然可以高效精准。

### 关键设计原则

意图识别这一步 **绝不能"猜",必须是"确认"**。所有后续步骤都基于这一步的输出,这里错了后面再准也是错。宁可在这一步多花几秒和用户确认,也不要在后五步白跑。

---

## 第二步:基础上下文准备 —— 这一步是现阶段架构的"核心承重墙"

### 为什么说这一步是核心承重墙

在完整形态里,归因靠运行时的多跳图谱展开;但现阶段不做 Link 构建,**归因能力几乎完全依赖这一步准备的上下文质量**。上下文里包含什么、以什么粒度包含、关系讲得多清楚,直接决定了后续大模型能不能做出深度分析。

换句话说:**上下文准备阶段就要把"可能需要的业务语义"一次性组装完整,而不是指望 Agent 运行时再去补**。这要求上下文准备这一步做得比完整形态还要扎实 —— 它是现阶段架构里最吃功夫的环节。

### 四件事组成完整上下文

**1. 本体对象上下文(向量 + 图检索)**

系统通过向量检索定位与问题语义相关的业务对象(比如"质量异常"会命中批次、质检记录、不良品等对象),通过本体知识库里已经维护好的 **静态关系描述**(Excel 里记录的对象之间的业务关系 —— "批次使用原材料"、"批次经过工序"、"工序在设备上进行"等)拉取相关的关联对象和业务流程图。

这里的"图检索"不是运行时在图数据库上做多跳,而是 **基于 Excel 里已经整理好的关系描述做关联展开** —— 相当于用 Excel 维护一份"静态的关系图",每次问题进来时按需检索出相关子图。这种做法在本体规模不大(几十到几百个对象)时完全够用,工程复杂度远低于引入图数据库。

**输出**:一份 **子本体片段** —— 本次问题相关的对象清单、每个对象的属性说明、对象之间的业务关系描述、关联的业务流程图、对应的物理表和字段映射。

**2. Skills(工具)上下文**

系统根据问题类型和用户权限,确定本次可调用的 Skills —— SQL 执行、统计分析、图表生成、报告生成等。Skills 是 Agent 的"工具箱",需要预先约束哪些可用,既出于性能也出于权限考虑。

**3. 指标维度上下文(向量检索 + 自动匹配)**

系统通过向量检索定位问题相关的指标(销售额、不良率、转化率),并自动选择最合理的分析维度(时间、地区、产品、客户)。**如果指标和维度匹配出现歧义或冲突** —— 比如"上月销售额"可以按"订单创建月份"也可以按"发货月份" —— **必须让用户手动选择**。

**4. 业务语义上下文**

这是容易被忽略但在现阶段特别重要的一层 —— **把本体知识库里的业务含义描述也打包进来**。不只是"有哪些对象、哪些字段",还包括:

- 这个指标怎么算
- 这类对象和那类对象的业务关系是什么
- 这个流程的关键节点在哪

这些业务语义描述让大模型在后续分析时能基于业务常识推理,而不是只看到冷冰冰的字段名。

### 上下文打包原则

所有信息打包成一个结构化的上下文对象,交给 Agent 作为工作输入。**这个对象的质量直接决定了推理的天花板** —— 上下文残缺、错误、冗余,Agent 再聪明也救不回来。打包时几个关键平衡:

- **宁可多带一点也不要漏**:后面再补会打断推理流
- **但不能全量加载**:会爆 token 也会引入噪声
- **精确召回是核心能力**:召回率低会漏关键信息,精度低会被噪声干扰
- **业务语义要完整**:对象关系、流程含义、指标口径这些描述必须清晰,让大模型能"看懂业务"而不是"猜业务"

### 本体知识库在这一步的形态

现阶段本体知识库维护在 Excel 里,典型包含几张表:

| 表名 | 内容 |
|---|---|
| **对象表** | 每个业务对象的名称、业务含义、关键属性、对应物理表 |
| **属性表** | 每个属性的名称、类型、业务含义、取值范围、计算方式 |
| **关系表** | 对象之间的业务关系描述、关系含义、业务场景 |
| **流程表** | 关键业务流程的步骤、涉及对象、关键节点 |
| **指标表** | 指标定义、计算口径、适用维度 |
| **术语表** | 业务术语和本体条目的对应关系 |

这些 Excel 表通过向量化处理后建立检索索引,上下文准备时按需检索拉取。**Excel 作为载体的优势是业务人员和数据团队都能直接维护,降低冷启动门槛**;劣势是规模和查询复杂度上有限制,但现阶段用足够了。

### 关键设计原则

这一步 **投入要比你以为的更大**。现阶段没有多 Agent、没有运行时图谱多跳,所有的"智能"都建立在"给 Agent 一个足够好的工作台"之上。Excel 知识库看起来简单,但要维护得好、检索得准、语义描述得清楚,工程量不小。**这一步做扎实,后面自然顺;这一步敷衍,后面怎么补都补不回来**。

## 第三步:Agent 思考与规划 —— 把"问题"拆成"可执行步骤"

### 核心任务

有了上下文,Agent 开始 **真正思考**。这一步不是直接生成答案,而是 **生成一个解决问题的计划** —— 分几步、每步做什么、需要什么数据、用什么工具、产出什么中间结果。这个计划就是后面执行的蓝图。

### Agent Loop 的形态

Agent Loop 的本质是 **"思考—行动—观察—再思考"的迭代循环**:

- **思考(Thought)**:基于当前上下文,我下一步该做什么?
- **行动(Action)**:调用某个工具或生成某个产出(SQL、查询、推理)
- **观察(Observation)**:看行动的结果是什么,是否符合预期
- **再思考**:基于观察调整下一步,直到完成任务或达到上限

在规划阶段,Agent Loop 的产出是一个 **结构化的执行计划**,类似:

```
计划:
  Step 1: 取数任务
    - 描述: 查询近 6 个月华东区按月聚合的销售额
    - SQL 任务: 待生成
    - 输出变量: monthly_sales_east
  
  Step 2: 趋势分析
    - 描述: 识别异常月份
    - 输入: monthly_sales_east
    - 输出: anomaly_months
  
  Step 3: 深度分析取数
    - 描述: 针对异常月份拉取客户、产品、订单维度的详细数据
    - SQL 任务: 待生成(基于 Step 2 结果动态构造)
    - 输出变量: detail_data
  
  Step 4: 综合分析
    - 描述: 基于上下文的业务关系做归因推理
    - 输出: analysis_conclusions
  
  Step 5: 可视化
    - 描述: 调用图表生成 Skill
    - 输出: charts
```

**这个计划是动态的** —— 后续步骤的执行结果会反过来修改后面的步骤。如果 Step 2 发现趋势没有显著异常,Step 3-4 可能被跳过直接进入总结;如果 Step 3 发现的数据指向了规划时没预料到的方向,Step 4 的分析重点会自动调整。这就是 Agent Loop 的价值 —— **计划不是一次性的瀑布流,而是边走边修**。

### Action 链的构建

执行计划的每一步都被表达为一个 **Action**,Action 之间通过数据依赖连成 **Action 链**。Action 有几种典型类型:

- **查询 Action**:生成 SQL 并执行
- **计算 Action**:调用统计分析工具
- **推理 Action**:调用大模型做综合判断或叙事生成
- **可视化 Action**:调用图表生成 Skill
- **校验 Action**:对中间结果做合理性校验

每个 Action 有明确的输入、输出、依赖、重试策略。**这是一个有向无环图(DAG),不是简单的线性流水线** —— 某些 Action 可以并行,某些必须串行。

### 本体知识库在这一步的支撑

规划本身就是基于上下文里的本体信息展开的 —— Agent 知道上下文里有哪些业务对象、它们的关系、相关的指标维度,才能规划出有意义的步骤。**上下文准备得好,Agent 规划就能贴合业务;上下文残缺,Agent 只能做泛泛的通用规划**。

### 关键设计原则

规划阶段的产出 **必须是可执行、可验证、可中断的**:

- **可执行**:每一步都能落到具体工具调用
- **可验证**:每一步有明确的成功标准
- **可中断**:任何一步出错都能优雅降级而不是整体崩溃

**好的规划比好的执行更重要** —— 执行错了可以重来,规划错了越执行越偏。

---

## 第四步:SQL 执行与数据获取 —— 从"想要数据"到"拿到数据"

### 核心任务

规划阶段产出了 SQL 任务,这一步负责把它真正执行并拿到数据。看起来简单,实际是 **最容易翻车的一步** —— AI 生成的 SQL 经常有语法错误、字段错误、口径错误、性能爆炸。所以这里需要 Agent Loop 做校验和修正。

### Text-to-SQL 的多重保障

**1. 基于本体的 SQL 生成**

SQL 不是从原始 schema 生成,而是基于上下文里已经组装好的 **对象-物理表映射** 生成 —— 大模型先想清楚"要查批次对象的不良率属性,过滤条件是产线 L3",然后通过本体知识库里的映射规则翻译成具体 SQL。**这一层抽象避免了大模型直接面对几百张表的混乱,大幅降低了字段错误率**。

**2. 静态校验**

SQL 生成后先做静态检查:

- 语法是否合法
- 字段是否存在
- JOIN 路径是否合理
- 是否有明显的笛卡尔积
- 是否符合权限范围

这一步纯规则,不调用大模型,快速过滤明显错误。

**3. Dry Run 校验**

对复杂查询先做 EXPLAIN 或在小样本上试跑,评估执行成本 —— 如果预估扫描量或耗时超过阈值,要么自动重写优化,要么告警让用户确认。**避免一个错误的 SQL 拖垮数据库**。

**4. 结果合理性校验**

SQL 执行后,Agent 看一眼结果:

- 返回 0 行?
- 返回的数字明显不合理(销售额是负数)?
- 字段类型不匹配预期?

这些情况触发 Agent Loop 的"再思考",反思是不是 SQL 写错了或者过滤条件太严,然后重新生成。

### Agent Loop 在这一步的形态

```
Loop iteration 1:
  生成 SQL → 静态校验 → Dry Run → 执行 → 看结果
  发现:返回 0 行
  反思:可能是 WHERE 子句里 product_type='高精度' 匹配不到
  
Loop iteration 2:
  调整 SQL → 执行 → 看结果
  发现:返回 1000 行,数据合理
  完成:数据加入上下文
```

**Agent Loop 的关键是"看结果再决定下一步",而不是一次性盲跑**。这是它和传统 ETL 的本质区别。

### 数据加入上下文

校验通过的数据被加入会话上下文,但 **不是直接把所有原始行加进去** —— 大数据集会爆 token。通常是:

| 数据规模 | 处理策略 |
|---|---|
| **小数据集**(几十行) | 直接加入上下文 |
| **中数据集**(几千行) | 做摘要统计后加入,原始数据存到临时存储,后续按需查询 |
| **大数据集**(几万行以上) | 只加入元信息(行数、列、统计量),数据本身存在外部,后续按引用访问 |

**这种分级策略让 Agent 既能感知数据全貌,又不会被海量数据淹没**。

### 关键设计原则

SQL 执行阶段 **安全大于效率,准确大于速度**。宁可多校验几次多花几秒,也不能让一个错误 SQL 直接执行 —— 错误数据进入后续分析的代价远大于多校验的代价。

---

## 第五步:深度分析和可视化 —— 从"数据"到"洞察"

### 核心任务

数据拿到了,真正的智能分析才开始。这一步要做三件事:

1. **基于上下文做归因分析**
2. **判断是否需要再次取数**(动态补全)
3. **生成最终分析和图表**(产出)

这是整个系统价值密度最高的环节。

### 现阶段归因的实现方式:上下文驱动而非图谱多跳

这是现阶段架构和完整形态的最大差异,也是最值得讲清楚的点。

**完整形态的归因** 依靠运行时沿本体 Link 做多跳探索 —— 从症状对象出发,按语义边一跳一跳展开,直到找到候选原因。

**现阶段的归因** 依靠 **上下文里已经准备好的业务关系描述 + Agent 的迭代推理** —— 第二步上下文准备时,已经通过本体知识库把"和当前问题相关的业务对象、它们之间的关系、业务流程"一次性组装进上下文。大模型基于这份"静态的关系地图"做推理,不需要运行时去图谱上爬。

**具体形态**:

```
Agent 看到销售额下降最明显的是产品 A
  ↓(基于上下文里"产品-客户-订单"的业务关系描述)
Agent 判断需要看客户侧数据,规划新的取数
  ↓(SQL Loop)
拿到客户数据后,发现某几个大客户订单减少
  ↓(基于上下文里"客户-客户经理-市场活动"的业务关系描述)
Agent 判断需要看客户经理变动和市场活动数据
  ↓(SQL Loop)
取数、综合、得出结论
```

**这种做法的本质是把"多跳"从运行时动作变成"规划时的 Agent 迭代"** —— Agent 通过 Loop 多次"想一步、取一次数、再想一步",每次决策都基于上下文里已有的业务关系描述和新拿到的数据。这个过程在效果上模拟了多跳,只是不依赖运行时的图谱结构。

**优劣对比**:

- **优势**:工程简单(不需要图数据库、不需要运行时图算法)
- **劣势**:归因深度依赖上下文准备的完整性 —— 如果第二步漏掉了某个关键业务关系,Agent 在这一步就找不到那条归因路径

**所以第二步的投入直接决定了这一步的能力上限**。

### 动态取数的迭代循环

归因过程中,Agent 经常需要再次取数 —— 初次取的数据不足以回答新冒出的问题。这时触发 SQL 生成和执行的 Loop(回到第四步的流程),新数据加入上下文后继续推理。

**这个嵌套的 Loop 是深度分析的引擎** —— Agent Loop 在外层驱动分析方向,SQL Loop 在内层确保每次取数准确。

### 综合分析

所有数据、统计结果、业务推理汇总后,大模型做最后的整合 —— 把结论翻译成业务叙事,显式标注证据来源、推理逻辑、置信度、未能回答的部分。**输出不是一个简单答案,而是一份带证据和推理过程的分析报告**。

### 可视化生成

报告中需要图表的部分,Agent 调用图表生成 Skill。**关键是图表类型不是固定的,而是 Agent 根据数据特征和问题语义动态选择**:

- 时序数据 → 折线图
- 分布对比 → 柱状图或箱线图
- 地理数据 → 地图
- 归因结果 → 桑基图或瀑布图

**生成式可视化比固定模板看板更贴合每次问题**。

### 本体知识库在这一步的支撑

这一步虽然不做运行时图谱多跳,但 **对本体知识库的依赖同样深** —— 分析过程中 Agent 频繁回头查上下文里的业务关系描述:

- 客户和订单是什么关系
- 这个指标的口径是什么
- 这个流程的下游节点有哪些

这些描述都来自本体知识库。**上下文准备阶段的功夫,在这一步集中兑现**。

### 关键设计原则

深度分析阶段要 **敢于多次取数但不能盲目扩散**。每一次取数都要有明确的假设和验证目标,不能为了"看起来深度"而堆叠步骤。**质量大于深度,可解释大于复杂**。每一步推理要能追溯到上下文里的具体业务关系描述或取到的具体数据,不允许凭空推断。

---

## 第六步:校验 —— 确保"漂亮的报告"是"正确的报告"

### 核心任务

分析报告生成后,在交付用户之前做 **最终校验**。这一步是 Agent Loop 的内部能力,目的是抓住前面所有步骤可能引入的错误 —— 逻辑错误、数据错误、推理跳跃、自相矛盾、与已知事实冲突。

### 多种校验机制

**1. 数据一致性校验**

- 报告里的数字是否和原始数据吻合?
- 是否存在算错、抄错、单位错?
- 是否前后矛盾(开头说销售下降 10%,结尾说下降 15%)?

**2. 逻辑一致性校验**

- 结论是否真的从证据推出?
- 有没有"听起来合理但其实没逻辑"的推理跳跃?
- 归因链条是否完整?

**3. 与本体知识库校验**

报告里的陈述是否和本体知识库里的已知信息冲突?如果报告说"产线 L3 在 4 月停产了",知识库里 L3 在 4 月有正常生产记录,这就是冲突。

**4. 自反式校验(Agent 自我质疑)**

让 Agent 自己扮演"挑刺者"的角色,主动质疑刚生成的报告:

- 这个结论是唯一解释吗?
- 有没有忽略的维度?
- 数据样本是否有偏差?

这种自反式检验能抓住主分析里的盲区。虽然现阶段是单 Agent 架构,但同一个 Agent 在不同阶段扮演不同角色(先做分析、再做质疑),依然能获得类似对抗检验的效果。

**5. 置信度标注**

校验通过后,给每个结论标注置信度:

- **高置信**:确定的结论
- **中置信**:有不确定的结论,说明不确定来源
- **低置信**:推测性的结论,明确说"这是基于有限数据的推测"

**显式的不确定性标注比假装全部确定更值得信任**。

### 校验失败时的处理

校验发现问题不是直接弹出错误,而是 **触发 Agent Loop 回到对应步骤修正**:

| 问题类型 | 处理方式 |
|---|---|
| 数据问题 | 回到第四步重新取数,或第二步调整指标 |
| 逻辑问题 | 回到第三步重新规划,或第五步重新分析 |
| 与知识库冲突 | 标注冲突并降低置信度,或主动询问用户 |

这个回退机制让校验不是"一票否决",而是"问题驱动的迭代"。

### 关键设计原则

校验阶段 **宁可保守不要冒进**。AI 生成的内容默认假设可能有错,通过校验来证明它对,而不是默认对然后期待校验抓错。**这是对用户负责的工程态度,也是产品被信任的基础**。

## 整体架构的几个关键洞察

把六步骤串起来看,现阶段这套架构有几个值得强调的设计哲学。

### 一、本体知识库是"全程支撑"而不是"某一步的工具"

本体知识库(虽然现阶段是 Excel)不是只在第二步用一下,而是贯穿六个步骤:

- **意图识别** 用它做术语映射
- **上下文准备** 用它组装工作台
- **Agent 规划** 基于它设计步骤
- **SQL 生成** 用它做对象-表映射
- **深度分析** 基于它的关系描述做归因推理
- **校验** 用它做事实比对

**本体知识库是这套系统的"脊椎",每一节都连着它**。

### 二、上下文准备是"现阶段的承重墙"

因为现阶段不做运行时图谱多跳、不做多 Agent 协同,**归因深度几乎完全由上下文准备的质量决定**。这意味着第二步的投入应该远超它表面的工程量 —— 本体知识库要维护得好、业务关系描述要写得清楚、检索算法要准、打包策略要合理。

**第二步做扎实,后面所有步骤自然顺;第二步敷衍,后面怎么补都补不回来**。

### 三、Agent Loop 是"多层嵌套"的自纠机制

整个流程里有多个 Agent Loop 嵌套:

- **外层 Loop**:六步骤的整体流程,某一步失败可回退到更早的步骤
- **中层 Loop**:深度分析阶段的迭代推理(分析—取数—再分析)
- **内层 Loop**:具体工具调用的校验循环(SQL 生成—校验—修正)

**这种多层嵌套让单 Agent 架构下依然有很强的自我修正能力**,任何一层出错不会立即崩溃。Agent Loop 是单 Agent 架构能做深度分析的关键 —— 它让一个 Agent 通过多次迭代达到接近多 Agent 协同的效果。

### 四、用户介入是"设计的一部分"而不是"失败的标志"

意图歧义需要用户消歧、指标维度冲突需要用户选择、低置信结论需要用户确认 —— **这些介入点不是系统能力不足,是产品设计的必要环节**。

盲目追求"全自动"在严肃分析场景下是反产品的 —— 用户对自己业务的判断力,在很多关键节点上比系统更可靠。产品要做的是把这些介入点设计得 **自然、轻量、有价值**,而不是粗暴地把所有事情自己扛下来。

### 五、复杂度自适应:轻问题轻处理,重问题重处理

简单查询走快速通道(意图识别 → 上下文准备 → SQL → 结果),不必启动深度分析和多次校验。复杂归因走完整流程多次迭代。

**资源消耗匹配问题价值,这是产品在生产环境可持续运行的基础**。

### 六、现阶段架构为未来演进留足空间

现阶段的 Excel 本体知识库、单 Agent、上下文驱动归因,并不是产品的终态,而是 **可以平滑演进的起点**:

| 现阶段 | 未来演进方向 | 触发条件 |
|---|---|---|
| Excel 本体 | 结构化本体图谱 | 规模和查询复杂度要求更高 |
| 上下文驱动归因 | 运行时 Link 多跳 | 归因深度要求提升 |
| 单 Agent + 多层 Loop | 多 Agent 参谋部式协同 | 场景复杂度要求更高 |
| 静态关系描述 | 带语义标签和因果效应的 Link Types | 需要做因果干预推演 |

**每一步演进都是增量的,不需要推翻现有架构**。这是一个务实但有远见的设计 —— 先把闭环跑通并产生价值,再按需要向更深的能力演进。

---

## 整体流程的一句话总结

> **用户提问 → 意图识别(确定要做什么)→ 上下文准备(基于本体知识库组装完整工作台)→ Agent 规划(拆解执行步骤)→ SQL 执行(取到数据)→ 深度分析(上下文驱动的归因推理 + 动态取数)→ 校验(确保正确)→ 输出报告**

**整个流程被本体知识库贯穿、被 Agent Loop 驱动、被用户介入点保障**。本体知识库让推理有结构,Agent Loop 让单 Agent 也能自纠迭代,用户介入让关键决策有保障。这三件事是现阶段架构能产出高质量分析的根本。

## 配套讨论:现阶段架构如何支撑"看结果 / 看原因 / 看未来"

### 看结果

对应六步骤的标准路径 —— 意图识别 + 上下文准备 + 规划 + SQL 执行 + 基础分析 + 可视化。

这条路径延迟低、覆盖广,是日常使用最高频的场景。

### 看原因

激活第五步的深度归因 —— Agent 基于上下文里的业务关系描述做多次迭代推理,通过 Agent Loop 动态取数验证假设,最终输出带证据链的归因结论。

现阶段的归因深度受限于上下文准备的完整性,**所以本体知识库的维护和上下文打包策略是这条能力的瓶颈也是抓手**。

### 看未来

现阶段能做轻量版 —— 基于历史数据趋势 + 上下文里的业务关系描述,让 Agent 推理"如果 X 发生,Y 可能会怎样"。深度的因果推断、仿真推演、多方案对比在当前架构下能力有限,是后续演进的方向。

**现阶段先把"基于现状的前瞻分析"做扎实,比虚张声势地说"支持决策推演"更务实**。

### 架构统一,能力分层

**三方向共享同一套六步骤架构**,只是深度分析阶段的投入和 Agent Loop 的迭代次数不同。架构统一,能力分层 —— 这让产品在不同问题上都能有匹配的回答。
