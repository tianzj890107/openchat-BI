# ChatBI Agent 按场景分析 SOP

## 1. 文档目的

本文档用于统一 ChatBI Agent 在不同业务问题下的分析路径、工具选择、证据标准和交付边界。适用于语义检索、图库检索、数据库查询、报表追问以及多轮分析场景。

核心原则：先确认问题和口径，再取数；先验证事实，再归因；结论强度不能超过证据强度；只完成用户要求的分析深度，不擅自扩展。

---

## 2. 通用六步主流程

会话 SOP 展示固定六步：`意图识别` → `本体模型匹配` → `深度思考&分析规划` → `数据获取和可视化` → `根因分析` → `决策行动`。以下各节是每一步的执行细则。

SOP 状态规则：

- SOP 是真实执行轨迹，不是静态清单：只有实际进入并完成的步骤显示绿色完成；
  当前正在执行的步骤显示进行中；尚未到达的步骤显示未开始。
- 第 5 步「根因分析」只在真正开始分析原因、贡献度、关联证据或根因链时才进入。
  L1 取数查询（例如“有多少订单”“销售额是多少”）执行第 4 步后直接进入第 6 步
  整理结论，不得产生第 5 步事件；L2 只做异常定位、不做原因分析时同样不进入
  第 5 步。禁止仅凭“执行过 SQL”判断发生了根因分析。
- 本轮不需要执行的步骤在结束时显示为「已跳过」（非绿色）：例如 L1 未做根因时
  第 5 步为已跳过，不能显示为绿色完成。`done` 只表示本轮成功结束，不代表六个
  业务步骤全部实际执行；未执行的步骤不会被 `done` 染绿。
- 回退循环（05→03、04→03、06→05 等）是真实跳转：回到前一步后，后续步骤重新
  计算为未开始，不得保留错误的绿色完成状态。

### 第一步：意图识别

先从完整语义判断问题属于 L1–L5，不得只按单个关键词机械分类。

| 等级 | 用户意图 | 典型问法 | 标准交付 |
|---|---|---|---|
| L1 | 查询、汇总、展示 | “上月收入多少”“列出可分析指标” | 数据、必要图表、简短结论 |
| L2 | 异常、偏差、对比、定位 | “哪里异常”“哪个区域下降最多” | 基准、差异、异常切片、结论 |
| L3 | 原因、归因、深挖 | “为什么下降”“根因是什么” | 根因证据链、验证结果、建议雏形 |
| L4 | 方案、优化、决策 | “怎么办”“给出改善方案” | 备选方案、效果、成本、风险、周期、推荐项 |
| L5 | 落地、执行、监控 | “怎么落地”“给执行计划” | 责任视角、时间节点、完成标准、监控指标、复盘机制 |

边界规则：

- L1 不主动做根因或建议。
- L2 只定位问题，不主动展开根因。
- L3 一旦输出“根因分析”，必须同时给出 1–2 条基于证据的“行动建议”或“建议雏形”。
- “怎么办、如何改善、给方案”属于 L4，不应降级为普通根因分析。
- “执行计划、落地、责任人、监控、复盘”属于 L5。
- 用户明确说“不分析原因”或“不要建议”时，尊重其边界。

### 第二步：本体模型匹配

从问题中提取：

- 用户角色或回答视角；
- 业务对象；
- 指标及其定义；
- 时间范围与对比基准；
- 组织、地区、客户、产品等维度；
- 分析范围、过滤条件和期望输出。

以下情况必须调用 `AskUser`，不能替用户猜测：

1. 一个术语对应多个不同口径，且上下文无法唯一确定；
2. 一个名词命中多个业务对象或指标锚点；
3. 指标存在多个合理的时间或业务口径；
4. L2 以上分析存在多个合理主下钻维度，用户没有指定；
5. 回答视角会显著改变判断标准或建议。

可以通过本体唯一确定时直接推进，避免无意义打断用户。

### 第三步：深度思考&分析规划

语义检索模式：

- 使用本体检索确认业务对象、属性、指标、维度、流程和物理映射；
- 优先使用已确认的指标定义和映射，不直接凭字段名猜口径；
- 远程本体模式优先使用语义查询工具，接口不支持或失败时再回退 `Ontology-FactQuery`。

图库检索模式：

1. 使用 `Ontology-TermDisambiguate` 做术语嫁接；
2. 使用 `Ontology-GraphContext` 锚定业务对象或指标并获取剪枝后的上下文；
3. 指标锚点自动上挂业务对象，并带出可下钻维度；
4. 只有 L3–L5 且已有上下文不足时，才调用 `Ontology-GraphExpand` 扩散上下游对象、流程和跨对象关系；
5. 上下文已经足够时不得为了“显得深入”而无边界扩散。

### 第四步：数据获取和可视化

L2 及以上多步骤任务开始时，使用待办工具拆成 3–6 个可验证步骤，例如：

1. 确认口径与基准；
2. 获取总体数据；
3. 定位主要异常切片；
4. 下钻并交叉验证；
5. 渲染表格或图表；
6. 汇总结论和建议。

取数优先级：

1. 已有报表数据或本轮可靠查询结果；
2. `Ontology-MetricQuery` 等语义数据接口；
3. 基于本体物理映射生成并执行 `Ontology-FactQuery`；
4. 接口或映射不足时，明确披露限制，不虚构结果。

SQL 执行要求：

- 只执行只读查询；
- 明确时间、范围、过滤条件、聚合粒度和单位；
- JOIN 必须有本体映射或可验证的字段关系；
- 默认限制结果规模，先聚合后明细；
- 0 行、异常值或口径明显不合理时，先检查过滤条件和映射再重试；
- 不得为了得到“合理数字”而反复修改口径。

### 第五步：根因分析

仅当用户问题属于 L3–L5（或最终正文确实包含根因分析章节）时才进入本步；L1/L2
只做取数与异常定位时不进入本步，结束时本步显示为已跳过。进入本步后，每项关键
结论至少回答：

- 使用了什么指标和口径；
- 对比基准是什么；
- 哪个切片贡献最大；
- 数据是否支持该判断；
- 是事实、关联、推断还是已验证原因。

结论等级：

| 等级 | 含义 | 可用措辞 |
|---|---|---|
| FACT | 查询直接得到的事实 | “数据显示”“实际为” |
| ASSOCIATION | 两个变化共同出现 | “相关”“伴随”“值得排查” |
| INFERENCE | 有业务链路支持但未完成排他验证 | “推测”“较可能”“候选原因” |
| VERIFIED | 有对照、时序、机制或独立证据验证 | “已验证”“主要原因” |

禁止把相关性直接写成因果。字段名、表名和模型常识只能用于提出假设，不能单独证明根因。

展示规则：

- 查询或计算产生核心数据后，必须调用 `TableGenerate` 或图表工具，不能只在正文手写 Markdown 表格；
- 时间趋势优先折线图；
- 分类对比、排名、差异优先柱状图；
- 构成且类别较少时可使用饼图；
- 多维指标下钻使用 `ChartGenerateMultiDim`；
- 每行数值完全相同或只有无信息量计数时，只使用 `TableGenerate`，不要强行出图；
- 图表不能替代口径说明和文字结论。

### 第六步：决策行动

输出使用纯文字标题和标准 Markdown，不使用装饰性表情符号。

结束前检查：

- 用户问题是否逐项回答；
- 指标、时间、范围、单位和对比基准是否清楚；
- 核心数字是否有查询或报表证据；
- 数据冲突是否已经协调或披露；
- L3 是否同时包含基于根因证据的建议；
- L4 是否给出方案比较和明确推荐；
- L5 是否给出责任、节点、标准、监控和复盘；
- 查询数据是否已经渲染为卡片；
- 是否错误地把假设写成事实。

## 3. 按场景执行 SOP

### 场景 A：单指标或清单查询（L1）

适用示例：“本月销售额是多少”“有哪些业务对象”“列出库存相关指标”。

执行：

1. 确认指标/对象和最小必要范围；
2. 唯一命中时直接查询，存在口径歧义时先 `AskUser`；
3. 查询数据或本体清单；
4. 使用 `TableGenerate` 展示明细；只有存在趋势或比较意义时才出图；
5. 用 1–3 句话回答结果与口径。

禁止：主动下钻原因、输出治理建议、把清单数量为 1 的结果画柱状图。

完成条件：数字/清单、范围、口径和单位明确。

### 场景 B：趋势、同比和环比分析（L1–L2）

适用示例：“近 12 个月收入趋势”“本月同比为什么差这么多”中的趋势定位部分。

执行：

1. 确认时间字段、时间粒度和同比/环比基准；
2. 查询完整可比时间窗，避免只取当前期；
3. 校验缺失月份、数据刷新日期和异常基数；
4. 计算绝对变化和变化率；
5. 用折线图展示趋势，用表格保留精确值；
6. 标注峰值、谷值、拐点和最大变化期。

完成条件：时间口径可比，异常期定位明确。用户未要求原因时停在 L2。

### 场景 C：排名、贡献度和结构分析（L2）

适用示例：“哪个区域下降最多”“收入主要来自哪些产品”。

执行：

1. 确认排名指标、排序方向、Top N 和“其他”处理方式；
2. 同时查询当前值、对比值、差额和贡献率；
3. 避免只按变化率排名而忽略小基数；
4. 使用柱状图展示排名，使用表格展示精确值；
5. 说明头部集中度和主要异常切片。

完成条件：总体变化能与各切片贡献勾稽，不能出现分项与总量不一致而不解释。

### 场景 D：异常检测和问题定位（L2）

适用示例：“有没有异常”“哪里出了问题”“本月波动是否正常”。

执行：

1. 明确正常基准：历史区间、预算、目标、同群组或业务阈值；
2. 先验证总体异常是否真实；
3. 按用户指定或确认的主维度下钻；
4. 对异常切片检查数据完整性、样本量和口径变化；
5. 输出异常位置、幅度、持续时间和影响范围；
6. 不主动进入根因，除非用户明确要求 L3。

完成条件：异常必须相对于明确基准成立，而不是仅凭数值大小判断。

### 场景 E：根因分析（L3）

适用示例：“销售额为什么下降”“质量问题的根因是什么”。

执行：

1. 先确认异常事实、影响量和主要异常切片；
2. 建立候选原因树：时间、组织、客户、产品、流程、活动或上下游对象；
3. 图库模式下，现有上下文不足时调用 `Ontology-GraphExpand` 获取有关系证据的候选路径；
4. 为每个候选原因设计验证查询，检查贡献、时序、机制和反例；
5. 至少进行一次交叉验证，不得仅依赖一张表或同一口径的重复查询；
6. 区分已排除、弱关联、候选原因和已验证原因；
7. 输出根因证据链，并给 1–2 条与已验证原因直接对应的建议雏形。

建议不得写“加强管理、持续关注”等空话，也不得声称尚未执行的动作已经生效。

完成条件：每个“根因”都有数据、业务链路和验证结果；证据不足时必须降级为候选原因。

### 场景 F：方案和决策建议（L4）

适用示例：“如何改善利润”“应该选哪个方案”“是否需要调整库存策略”。

执行：

1. 继承并核对问题事实和根因证据；
2. 明确目标、约束和决策标准；
3. 形成至少两个可比较方案，必要时包含“不行动”基线；
4. 比较预期效果、成本、风险、周期、依赖和可逆性；
5. 标明哪些效果有数据依据，哪些属于估算；
6. 给出推荐方案及适用条件；
7. 说明需要业务负责人确认的关键假设。

完成条件：有明确推荐，不只是罗列选项；推荐能够追溯到已验证问题和约束。

### 场景 G：执行计划和闭环管理（L5）

适用示例：“给出落地计划”“怎么监控改善效果”“安排责任人与复盘”。

执行：

1. 将推荐方案拆成阶段和里程碑；
2. 为每项动作指定责任视角，不虚构具体人员姓名；
3. 定义开始条件、完成标准和依赖；
4. 配置领先指标、结果指标、预警阈值和检查频率；
5. 明确试点、扩大、暂停或回滚条件；
6. 设置复盘时间、输入数据和决策出口；
7. 用表格交付行动计划，必要时补充风险清单。

完成条件：计划可执行、可验收、可监控、可复盘。

### 场景 H：多维下钻分析

适用示例：“从时间、区域、产品多个维度分析收入变化”。

执行：

1. 指标存在多个合理维度且用户未指定时，调用 `AskUser`；
2. 确认一个主维度和若干辅助维度；
3. 每个维度使用相同指标、时间和过滤口径；
4. 先查总体，再查各维度，避免维度结果脱离总量；
5. 使用 `ChartGenerateMultiDim` 提供维度切换；
6. 比较不同维度是否指向同一异常群体；
7. 防止把多个高度重合维度当成独立证据。

完成条件：各维度口径一致，主结论能够回到总体指标。

### 场景 I：报表追问

适用示例：“这张报表里下降最大的是什么”“解释刚才图里的异常点”。

执行：

1. 继承当前报表、筛选条件和 AnalysisContext；
2. 优先使用报表已有数据，缺少必要粒度时才补查数据库；
3. 明确引用的是哪张图、哪张表、哪个筛选状态；
4. 不重复查询报表已经提供且口径一致的数据；
5. 用户改变范围、指标或维度时，只更新对应上下文，不清空无关条件；
6. 报表数据与补查结果冲突时先做 reconciliation。

完成条件：回答可追溯到当前报表状态，不把其他会话或默认筛选混入。

## 4. 异常与降级 SOP

### 4.1 术语、指标或锚点不唯一

- 列出 2–8 个有实质差异的候选项；
- 使用 `AskUser` 说明差异；
- 用户确认前不执行正式取数；
- 选择结果加入本轮上下文并在后续沿用。

### 4.2 查询返回 0 行

按顺序检查：

1. 数据源和 Schema 是否正确；
2. 时间范围是否超出数据覆盖；
3. 枚举值、大小写和空值处理；
4. JOIN 是否过度收窄；
5. 指标物理映射是否有效。

仍无数据时，明确回答“当前条件下无数据”，并列出已核验条件。不得把 0 行解释为业务值为 0。

### 4.3 数据冲突

- 比较数据源、刷新时间、过滤条件、时间字段、单位、去重和聚合口径；
- 能协调时给出统一结果和冲突原因；
- 不能协调时并列披露，不挑选更符合预期的数字；
- 冲突未解决前，不得基于其中一个结果做强因果或决策结论。

### 4.4 Proxy 指标或替代数据

- 明确标注“代理指标”；
- 说明它能观察什么、不能证明什么；
- 不得把 Proxy 当作用户原始指标；
- 关键决策依赖原指标时，应请求补充数据或降低结论等级。

### 4.5 SQL、语义接口或图工具失败

- 先修正参数、映射或 SQL，避免原样无限重试；
- 远程语义接口不支持时，可在确认物理映射后回退 `Ontology-FactQuery`；
- 图库扩散失败时使用已有 `Ontology-GraphContext` 完成可支持部分；
- 图表失败不影响事实结论，但必须保留表格展示；
- 工具持续失败时说明已完成部分、失败点和缺失影响。

### 4.6 模型、网络或流式中断

- 不把半截输出当作完成答案；
- 保留已经确认的用户口径、查询结果和待办状态；
- 恢复时从最后完整步骤继续，不重复已成功工具调用；
- 模型切换后重新确认参数兼容，但不改变业务口径；
- 无法恢复时向用户说明断点和下一步，而不是输出未经验证的结论。

### 4.7 数据不足以支持根因

输出结构：

1. 已确认事实；
2. 已排除因素；
3. 候选原因及当前证据；
4. 尚缺数据；
5. 下一步验证查询。

不得为了满足“根因”标题而虚构确定性。

## 5. 工具选择速查表

| 任务 | 首选工具 | 使用条件 |
|---|---|---|
| 术语消歧 | `Ontology-TermDisambiguate` + `AskUser` | 多口径且无法自动唯一确认 |
| 本体上下文 | `Ontology-SemanticQuery`、`MetricCalculation`、`Ontology-EntityDescribe` | 语义检索或核对单项定义 |
| 图库锚定 | `Ontology-GraphContext` | 图库模式每次问题的基础上下文 |
| 根因扩散 | `Ontology-GraphExpand` | 仅 L3–L5 且基础上下文不足 |
| 指标数据 | `Ontology-MetricQuery` | 远程语义接口支持当前指标 |
| 明细/聚合查询 | `Ontology-FactQuery` | 已确认表、字段、JOIN 和口径 |
| 表格 | `TableGenerate` | 所有需要精确展示的核心数据 |
| 单维图表 | `ChartGenerate` | 趋势、排名、对比或构成有视觉价值 |
| 多维图表 | `ChartGenerateMultiDim` | 同一指标需要多个维度切换 |
| 用户确认 | `AskUser` | 口径、锚点、维度或视角无法唯一确定 |
| 多步进度 | 待办工具 | L2 及以上、需要 3–6 个执行步骤 |

## 6. 最终输出模板

### L1

```markdown
## 结论

直接回答核心结果，并注明时间、范围、单位和口径。

## 口径说明

仅列必要定义和数据截止时间。
```

### L2

```markdown
## 结论

说明异常位置、幅度、影响范围和对比基准。

## 关键发现

- 总体变化
- 主要异常切片
- 数据质量或口径注意事项
```

### L3

```markdown
## 结论

说明主要原因及其证据等级。

## 根因分析

按“异常事实 → 候选原因 → 验证数据 → 判断”组织证据链。

## 行动建议

给出 1–2 条与已验证原因直接对应的具体动作。
```

### L4

```markdown
## 结论

明确推荐方案。

## 方案比较

比较效果、成本、风险、周期和依赖。

## 推荐理由

将推荐与事实、根因和约束对应起来。
```

### L5

```markdown
## 结论

说明执行目标和优先级。

## 执行计划

用表格列出阶段、动作、责任视角、时间节点和完成标准。

## 监控与复盘

列出指标、阈值、频率、复盘节点和调整条件。
```

## 7. Agent 禁止事项

- 未确认口径就正式取数；
- 用字段名、表名或常识替代业务证据；
- 把相关关系写成确定因果；
- 数据冲突时只选择其中一个结果；
- 0 行直接解释为业务数值 0；
- 用代理指标冒充原指标；
- L1/L2 擅自升级到根因或方案；
- 输出根因后不给基于证据的行动建议；
- 查询后只写 Markdown 表格而不调用渲染工具；
- 没有比较意义时强行生成图表；
- 工具失败后无限重复同一请求；
- 模型中断后重复已经成功的工具调用；
- 虚构已经执行的动作、具体责任人或未来效果。

## 8. SOP 验收清单

每轮结束前，Agent 应能够对以下问题回答“是”：

- 我是否正确识别了 L1–L5？
- 所有关键术语、指标、时间和范围是否唯一明确？
- 查询是否基于本体映射或可信报表上下文？
- 核心数据是否经过合理性和勾稽检查？
- 图表类型是否与数据关系匹配？
- 结论措辞是否匹配证据等级？
- 根因是否经过独立验证，而不是只有相关性？
- 建议是否对应具体根因和数据切片？
- 用户要求的交付层级是否全部完成且没有越界？
- 不确定性、冲突和数据限制是否已经披露？
