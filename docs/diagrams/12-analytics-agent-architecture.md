## 一图读法

整张图自上而下是**六层能力、二十三个能力块**，每一层用一个横向贯通的能力区块表示，区块左上角标注层名：

| 顺序 | 层次 | 能力块 | 这一层回答的问题 |
|---|---|---|---|
| 第一层 | 提问受理层 | 3 | 一次提问从哪里来，要不要带上上一轮的上下文 |
| 第二层 | 安全与合规把关层 | 1 | 这条请求该不该答 |
| 第三层 | 判断与分流层 | 4 | 到底在问什么，问到哪一层，信息够不够 |
| 第四层 | 本体语义层 | 5 | 业务说法、口径、对象、权限以哪一份为准 |
| 第五层 | 取数与洞察层 | 5 | 去哪里取事实与知识，怎么对比、找问题、查根因、看走势 |
| 第六层 | 交付与守门层 | 5 | 结论怎么组织、行动建议怎么给、执行怎么落地、交付前谁来把关 |

块与块之间的连线表示业务动作的流转方向，连线上的文字就是这一步在业务上做了什么；
同层并列的能力之间用虚线相连，表示它们属于同一层、需要一起使用。

其中**两层承担的是“标准”而不是“动作”**：第二层（安全与合规把关）决定“能不能答”，
第四层（本体语义层）决定“按哪一套说法答”。这两层都不产出数据，但它们排在取数之前。

## 本体是什么，在这张图里起什么作用

**本体不是一个数据库，而是这家公司做分析时唯一认可的一套业务说法。** 它把散落在各个系统、报表、
口径文档里的业务名词、计算规则、对象关系收敛成一份互相不打架的定义。在这张图里，本体单独占
第四层（橙色），因为它同时是三种东西：

1. **业务名词的统一说法**：同一个词在采购、库存、财务嘴里可能指不同的东西，本体负责给每个词
   一个确定含义，并说明它和别的词是什么关系。
2. **指标口径的唯一出处**：一个指标怎么算、统计范围包含什么、排除什么，只认本体里的那一份；
   取数时按这一份口径去取，不按各人理解临时拼。
3. **业务说法到数据的翻译层**：用户问的是业务语言（供应商、物料、账龄、缺陷率），本体负责把它
   落到实际有哪些业务数据、按什么规则对上，因此智能分析 Agent 才不需要用户会说“数据语言”。

在图上这一层用五个块展开：**本体（业务统一说法）→ 指标口径与定义 → 业务对象与关系 →
业务到数据的映射 → 权限与可见范围**。前四块是“语义”，最后一块是“边界”：即便口径清楚，
谁有权看哪些数据仍要单独确认。第四层与第五层之间有一条加粗连线“按本体口径取数”，
表示**取数必须先过本体**；第三层到第四层的加粗连线“先到本体对齐业务说法”，表示
**判断完问题类型就要先回到本体定说法**。

这也是本图与图 11 的分工：图 11 说明本体这一层在平台里由谁提供，本图说明智能分析 Agent
在回答问题时如何使用它。

## 分析深度的五级递进（L1 → L5）

同一个问题，深度可以差很多。智能分析 Agent 不把“是多少”和“该怎么改善”当成同一类问题，
而是在判断阶段就把深度定下来，再决定要暴露哪些能力、要交付到什么程度：

| 深度 | 名称 | 典型问法 | 交付落点 |
|---|---|---|---|
| L1 | 取数 | 是多少、有哪些、查一下 | 只给数据、图表和结论 |
| L2 | 找问题 | 有没有问题、哪里异常、波动多大 | 点出发现的问题，不展开原因 |
| L3 | 根因分析 | 为什么、什么原因、根因在哪 | 根因证据链，并给出 1–2 条建议雏形 |
| L4 | 行动建议 | 该怎么办、如何改善、给个方案 | 方案对比（效果/成本/风险/周期）+ 推荐项 |
| L5 | 执行与监督 | 怎么落地、排期、谁来跟、怎么做复盘 | 责任视角、时间节点、完成标准、监控与复盘 |

图上这条递进落在两层里：第五层按 **L1 取数 → L2 找问题 → L3 根因** 排布，第六层接着
**L4 行动建议 → L5 执行监督**。两层之间有一条加粗连线“根因升到行动建议”，第六层内部
“行动建议 → 执行落地与监督”同样加粗：**没有根因证据就不给方案，给了方案就要能落到执行**。

需要强调的是，层级是**按问句语义判定**的，不是按关键词硬跳：用户只问“是多少”，就只交付 L1，
不会硬塞根因和建议；用户直接说“给个方案”，就按 L4 交付，但前置的事实与根因至少要补齐，
不凭空给方案。

## 业务流转

1. **提问先过合规红线**：业务用户提出问题后，先由安全与合规把关判断这是不是索取凭据、删除或覆盖
   数据、越权查看、打探内部环境的请求；是红线问题就当场拒绝，不往下走，也不带出任何内部信息。
2. **被其他场景调用**：别的业务场景要用同一套分析能力时，也从同一个入口进来、走同一道把关，
   不另起一套。
3. **带上会话上下文**：多轮追问时把上一轮说过的对象、范围、条件一起带上，避免每轮都重新问一遍。
4. **合规通过后判断问题类型**：判断这次是在问事实数字、问指标口径、问原因、要处理建议，还是
   要看未来走势。
5. **这次问到哪一层**：在判断阶段就把分析深度定下来（L1 取数 / L2 找问题 / L3 根因 /
   L4 行动建议 / L5 执行监督），后面按这一层决定交付到什么程度。
6. **检查信息是否完整，缺条件先问清**：看时间范围、对象范围、统计口径这些条件齐不齐，
   不齐就先向用户澄清与追问，不带着猜测往下走。
7. **先到本体对齐业务说法**：需要出数或出建议时，先回到本体确认指标怎么定义、统计范围包含什么、
   对象之间什么关系、业务说法落到哪些数据，并按职责确认这次能看到哪些数据。口径不确认，
   不进入取数。
8. **按本体口径取数**：口径确认后再取用业务事实，与沉淀的业务知识一起支撑分析。
9. **逐级递进地看**：先看事实是多少、有哪些（L1）；再做对比与趋势，找出哪里异常（L2）；
   再归因与诊断，说清为什么会发生（L3）；必要时做预测与情景推演，并说明这是基于假设的推演。
10. **形成结论与依据**：把取到的证据组织成结论，写清依据、适用范围和限制。
11. **根因升到行动建议**：有 L3 的根因证据，才在此基础上给 L4 的行动建议——方案、优先级、
    预期影响，并说明推荐哪一条、为什么不推荐别的。
12. **定方案后落到执行**：按 L5 把选定的方案拆到责任视角、时间节点和完成标准，并约定后续
    跟踪与复盘方式。
13. **校验通过后交付**：交付之前由质量与真实性把关再核一遍，拦下没有依据的数字、把相关说成
    因果的说法、拿代理指标冒充目标指标的说法；通过后把结果讲给业务用户，并说明本次的口径、
    限制和下一步。

---

## 一句话结论

**先守红线、再懂问题、回到本体、逐级递进**：这条链路把安全把关放在最前面，把本体口径与权限
确认放在取数之前，把真实性校验放在交付之前，并且让分析深度一级一级往上走——所以它给出的是
**能追溯依据的分析结论**，而不是看起来像答案的数字，也不是没有根因支撑的行动方案。

  `scrollHeight 900`，刚好铺满一屏不出现滚动条，最小投影文字 8.91px ≥ 6px 门槛）。这些是自动化

  `<html data-theme="dark">` 写死，运行时按 `?theme=` → 浏览器本地存储 → 操作系统浅/深色偏好
  依次解析，所以在深色系统的机器上双击打开就是深色。因此 `deliver` 之后必须再执行一次：
